# Registry sync production investigation

## Confirmed findings

The exact public response `503 / UNAVAILABLE / Service temporarily unavailable.` is generated by `src/lib/api/handler.ts:errorResponse` for `DatabaseUnavailableError` or a MongoDB server error with code 8000 and a space-quota message. Provider HTTP errors do not map to this response.

POST execution: origin check and rate limit -> database connection -> authenticated active session -> owner/internal and registry.sync permission checks -> JSON validation -> country/provider/day validation -> stale-run update -> running-run lookup -> sync-run insert -> schedule background execution -> return sync ID. Background execution fetches registrations, normalizes them, upserts companies and contact provenance, queues research, fetches roles, rescoring, snapshots, final run/country updates and audit. Provider errors in execution are recorded as FAILED/PARTIAL runs, rather than propagated to the already-completed POST.

Storage exhaustion is a leading hypothesis when reads succeed and starting a sync returns this 503: stale-run cleanup or run insertion may reject writes before any registry fetch. A regression test reproduces this path. It is not a confirmed production root cause without the production runtime error or Atlas quota evidence.

Production is the Vercel business-operator project in siddiks-projects-06015787. Deployment dpl_HVSALDhNkW96jswNw294CGLtbzFb has the exploretechify.com alias. Read-only Vercel inspection confirmed Node 24.x, iad1 and Fluid Compute. Production variable names include MONGODB_URI, AUTH_SECRET, NEXT_PUBLIC_SITE_URL, DEMO_MODE and SEED_DEV_ACCOUNTS. The API omitted their values; value correctness and database size could not be verified. No production settings or database records were changed. The installed Vercel CLI 34 returned build logs; runtime logs were not obtained.

One read-only request to the official Bronnoysund API, bounded to one record for 2026-11-05, returned HTTP 200 with the expected page/embedded response shape (1088 ms). No record contents were printed. This establishes availability from the investigation machine only, not Vercel egress or historical availability. There is no evidence justifying changing provider URLs, authentication or retries.

## Changes

- src/app/api/registry/sync/route.ts: enable scoped diagnostics, explicitly select Node runtime, set maxDuration to 300 seconds, and register background work with Next.js after.
- src/features/registry/sync.ts: injectable scheduler, stage diagnostics around preparation and run creation, sanitized execution/bulk-write failures. Existing authenticated behavior and ingestion remain intact.
- src/features/registry/http.ts: upstream status, attempt and duration diagnostics without URLs/headers/body contents; remove upstream response-body excerpts from thrown errors.
- src/lib/diagnostics.ts: structured error allowlist that excludes messages, stacks, records and credentials.
- src/lib/api/handler.ts: opt-in route stage diagnostics; avoid raw unhandled-error logging when structured diagnostics are enabled. Public error contracts remain unchanged.
- tests/registry-production.test.ts: quota rejection before scheduling, one scheduled isolated empty sync and concurrent-start reuse, upstream 429 status and log sanitization.

The serverless lifetime issue is separate from the reported 503: an untracked promise may stop after the response. Next.js after extends its lifetime within the configured route duration. It is not a durable queue and does not guarantee completion of long backfills. No queue or unrelated architecture changes were introduced.

## Production configuration and deployment validation

1. In Vercel Runtime Logs, filter POST /api/registry/sync and inspect [registry.sync]. A database_capacity category/code 8000 confirms storage exhaustion. Check Atlas cluster-wide data plus index usage and tier quota. Restore capacity by increasing the tier/storage or following a separately approved retention plan. Do not delete data as part of this fix. No environment variable can bypass an exhausted quota.
2. For database_configuration, verify production MONGODB_URI has the intended explicit database name and a valid credential. Atlas must allow Vercel egress and the account must have required write permissions. Local fallback MongoDB is development-only. Do not set ALLOW_LOCAL_DB=true on Vercel. MONGODB_DNS_SERVERS is optional and should be set only for an evidenced resolver issue.
3. Verify AUTH_SECRET is at least 32 characters, NEXT_PUBLIC_SITE_URL=https://exploretechify.com, DEMO_MODE=false and SEED_DEV_ACCOUNTS=false. Production has these names but their values are unverified. BRREG_API_URL is optional; the default is https://data.brreg.no/enhetsregisteret/api and requires no API key. Do not add a speculative override.
4. For a controlled production validation, temporarily set REGISTRY_MAX_PER_RUN=1 and REGISTRY_PEOPLE_PER_RUN=0 in Production, redeploy the reviewed change, and sign in as an authorized owner. Trigger one NO DATE sync for one known past day. It will intentionally be PARTIAL if the source has more than one record because of the cap. Poll GET /api/registry/sync/{id}; confirm final state, counts, duration and the absence of new 503s. This performs bounded real writes; no production sync was run during this investigation.
5. Inspect upstream_response/upstream_request diagnostics for HTTP 429/403/5xx, timeout or DNS codes. Compare those logs with the successful read-only external probe. Restore the prior caps and redeploy after bounded validation. Do not use BACKFILL for this check.
